# ADR-0010: 工件卷并发写验证 — 单写者模型正当性

> 状态：已接受
> 日期：2026-09-02
> 关联计划：`docs/plan/mvp-preparation.md` A4

## 背景

架构设计采用「单写者模型」——同一时刻仅一个写角色修改源码。需验证并发写的实际损害程度。

## 决策

### 实测数据

两个进程各向同一文件追加 1000 行（预期 2000 行）：

| 指标 | 值 |
|---|---|
| 预期行数 | 2000 |
| 实际行数 | **501** |
| writer1 行 | 231 |
| writer2 行 | 270 |
| 数据丢失率 | **75%** |

### 结论

**并发写同一文件导致严重数据丢失**。单写者模型不仅有理论正当性，更有实测数据支撑：

1. 文件追加操作非原子，并发写互相覆盖
2. Docker Volume 在本地文件系统上行为一致（NFS/SMB 更严重）
3. 即使加文件锁，代码层面的冲突（两人改同一函数）仍需串行解决

### 实现策略

1. **Scheduler 层强制串行**：写角色任务节点在 DAG 中标记 `Writer: true`，Scheduler 对所有 Writer 节点串行执行
2. **审计校验**：`.aicodingagentteam/audit/` 记录写操作时间戳，校验无并发写
3. **文件锁兜底**：写角色获取 `.aicodingagentteam/write.lock` 后才修改源码

## 后果

- 正面：单写者模型有硬数据支撑，实现方向明确
- 负面：串行执行降低写角色吞吐量（但代码质量 > 速度，符合设计原则）
- 后续：NFS/SMB 网络文件系统需额外验证锁语义（已在 `03-系统设计与实施规划.md` 风险表中记录）
