# ADR-0001: 选择 Go 而非 Rust 作为开发语言

> 状态：已接受
> 日期：2026-09-02

## 背景

参考项目 [ref-project] 使用 Rust 实现。本项目需决定沿用 Rust 还是改用 Go。技术考量：容器化编排、并发模型、团队可维护性、CLI 调用调度。

## 决策

选择 **Go**。

关键理由：
1. **并发模型天然适配 Agent 编排**：goroutine + channel 模式完美匹配「并行评审角色 + 串行写角色」的调度需求
2. **容器生态成熟**：Go 静态编译产出极小镜像（< 20MB），Docker 多阶段构建简单，Rust 需处理 musl/glibc 兼容
3. **A2A/Redis/gRPC 生态**：go-redis、grpc-go、redis Pub/Sub 客户端均为一等公民
4. **团队可维护性**：Go 语法简单，上手快，AI 编码 CLI（Codex 自身）对 Go 支持成熟
5. **参考项目差异**：[ref-project] 单二进制分发，本项目是容器化多容器，Go 的交叉编译 + 小镜像优势更大

## 后果

- 正面：开发效率高，镜像小，并发模型直观
- 负面：无 Rust 的内存安全保证（但本项目无底层 unsafe 操作，影响小）；GC 暂停需关注（A2A 消息量大时）
- 后续：性能关键路径（BM25 检索、向量推理）可考虑 CGO 调 Rust 库，但 MVP 不需要
